## Decision and limits

Prepare these changes for preview and review; do not treat this report as proof that live LCP improved. No production deployment or Squarespace edit was performed. The actual LCP element and its timing breakdown still require a browser trace. No causal link between performance and zero conversions has been established.

Baseline supplied in the operating report: preceding seven days, desktop main website LCP 11.3 seconds (291 measurements), diagnostics LCP 12.6 seconds (417). The aggregation statistic, route mix, device definition, internal/bot filters and metric implementation must be confirmed from the reporting query before comparison. Do not silently reinterpret these numbers as p75. Small mobile samples do not establish a reliable device difference.

## Verified findings

| Finding | Evidence and implication | Scope of proof |
| --- | --- | --- |
| Diagnostics loads unrelated page code at startup | Original Vite build: entry JS 421.18 KB, gzip 129.09 KB; CSS 130.54 KB, gzip 25.37 KB. App statically imports index, quizzes, free Pulse and plan. | Verified bundle cost; contribution to 12.6-second LCP unmeasured. |
| Live homepage has large embedded image payloads | Fetched HTML 1,127,246 bytes; nine img data URLs contain 480,184 characters. Additional data URLs occur in CSS. | Verified decoded response/source size, not compressed transfer size. |
| Repository homepage is not the current live design | Live uses `#bcx` October redesign; repository `embed/homepage.html` is an older implementation. | Blindly pasting the old file would regress the live site. |
| Homepage loads multiple font stylesheet links | Live HTML includes Cormorant Garamond/Montserrat and two Playfair/Inter stylesheet links. Repo header includes Google Fonts. | A blocking stylesheet chain exists in markup; actual font use, request deduplication and time cost need a waterfall. |
| Native Squarespace logos remain in markup | Four eager, high-priority img elements, two unique URLs, each requests `format=1500w`. The custom page hides the native header. | Potential unnecessary loading/decoding; four elements do not necessarily mean four network downloads. |
| Homepage has no iframe | No iframe element in fetched homepage HTML. | Iframe behaviour cannot explain this homepage's LCP. Other website routes can differ. |
| Legacy embed hostname redirects | HTTP request to `https://bluechip-diagnostics.vercel.app/workplace-read` returns 308 to `https://check.bluechip-people-strategies.com/workplace-read`. | One avoidable navigation redirect for source embeds still using that hostname. |
| Iframe discovery waits for footer JavaScript | Source frames use `data-bc-diag-src`, not `src`; footer forwards UTMs and assigns src, retaining `loading="lazy"`. | Discovery delay and lazy loading can affect embedded readiness. Parent/child LCP is not an interchangeable metric. |
| Fonts and analytics are already partly optimized | Diagnostics fonts are local WOFF2 with unicode ranges and `font-display: swap`; GA is async; PostHog SDK loads asynchronously. | Their presence is not proof they cause LCP. Repeated font-face URLs are normally deduplicated. |
| Desktop-only visual path exists | Plan page lazily imports an 81 KB Plasma/WebGL chunk on capable desktop; reduced motion, mobile and iframes use CSS. | Plausible device-specific rendering cost on plan routes, not a verified cause on the free Pulse route. |

## Implemented changes, pending review/deployment

Diagnostics: React lazy route imports with an accessible loading status; CSS and page-specific code are fetched for the requested route. A preload starts the commonly used Latin Inter font before CSS font discovery. Analytics, replay, attribution, API behaviour, event names and consent/internal-device handling remain intact. Redirect tests now await lazy page rendering.

New build: entry JS 236.03 KB (gzip 76.10 KB), a 44% entry-byte reduction. Entry CSS 28.99 KB (gzip 6.39 KB). These are NOT total route bytes: the free Pulse also needs its 38.37 KB page chunk, 16.75 KB shared Pulse chunk, 21.05 KB shared CSS and smaller SEO/analytics modules. Plan and quiz routes have different totals. Lazy loading adds a request dependency; compare cold-cache traces, not just bundle size. Layout must verify that styles formerly shared through eager imports still apply correctly.

Website branch: `embed/homepage-performance-2026-10-31.html` is a separate replacement candidate extracted from the current live main Code Block. It substitutes 11 data URL occurrences with 10 existing hosted assets; all 10 destinations returned HTTP 200 and matched repository bytes by SHA-256. Restoring those data URLs reproduces the original code block byte-for-byte, including all three scripts, copy and CSS. Block size falls from 648,605 to 343,311 bytes (305,294 bytes / 47%); this is about 27% of fetched homepage HTML, not a guaranteed 27% transfer or LCP reduction. External images now have a network dependency, with the benefit of independent loading and reuse. A remaining unmatched inline PNG is preserved. The old homepage file is deliberately retained.

`embed/diagnostic-iframe-embed.html` and `embed/diagnostic-codeblocks-full.html` now use the canonical check hostname in frame data attributes, eliminating the verified redirect without changing UTM forwarding, sizing or lazy behaviour. These are historical templates; apply only where they match actual live blocks.

## Measuring causes and improvement

1. Preserve the original reporting query and its seven-day desktop baseline. Split by hostname, pathname, embedded versus top-level, browser/OS, viewport and release; exclude internal/QA and bots consistently. Confirm units and whether 11.3/12.6 are means, medians or percentiles. Inspect outliers and counts before attributing the desktop/mobile gap.
2. Before/after use the same Chrome version, desktop viewport (1440×900), device, network/CPU throttle, consent state and cache state. Run at least five cold-cache and five warm-cache loads of homepage, free Pulse direct, plan, and an actual embedded diagnostic page. Keep each lab median and range separately from field data. Capture Performance trace/screenshots and Network HAR; record LCP element, time to first byte, resource load delay, resource duration, render delay, long tasks, font requests and image transfers. Chrome's application-panel filters and recording must be consistent.
3. In controlled local/preview runs, compare analytics enabled versus blocked (GA, then PostHog/replay separately); never compare a stripped preview to production and call it a performance fix. Compare plan `?glass=css` to normal desktop separately. Disable first-screen reveal animations in a local override for another experiment. These are hypotheses to test, not reasons to remove tracking or design wholesale.
4. For frames, trace both parent and child. Record parent navigation start, footer execution, frame navigation start, redirect chain and child LCP. PostHog running inside the child does not automatically include the earlier parent navigation/iframe wait. Determine which context the operating report counted; do not add or compare unrelated LCP clocks.
5. Keep analytics configuration unchanged across rollout. Record release times for Squarespace and diagnostics independently. Compare a complete subsequent seven-day window with the supplied baseline, using the identical statistic/query plus p75, sample count and route/device mix. Report both absolute seconds and percentage change. Aim for p75 LCP ≤2.5 seconds; if the supplied baseline is a mean, report mean separately. Extend the observation period when samples are sparse rather than declaring a mobile win.
6. Verify CTA and assessment-start instrumentation in QA, then follow qualified inquiries, starts and completions per eligible visitor separately. Zero starts/inquiries alone cannot identify a performance cause. Do not claim a conversion lift without adequate comparable traffic.
